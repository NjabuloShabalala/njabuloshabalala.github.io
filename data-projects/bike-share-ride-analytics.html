Bike-Share Ride Analytics — BigQuery SQL

Google BigQuery SQL

Exploratory analysis of a bike-share service's ride, user, and station data to understand data quality, ridership patterns by membership type, peak demand hours, popular stations, and signup seasonality — with the goal of informing fleet allocation and membership strategy.

Key Results

  • Peak demand identified at two distinct windows — 7am and 3pm — aligning with commuter start/end-of-work patterns rather than a single midday peak.
  • Data quality issue caught early: 106 rides under 2 minutes and 1 zero-distance ride flagged as likely false starts, preventing them from skewing average ride duration and distance metrics.
  • Two distinct rider segments surfaced from membership-tier analysis: casual riders show higher average distance and duration (consistent with tourist/leisure use), while subscribers make up the highest-volume, most consistent rider base.

The Problem

The bike-share operator had raw ride, user, and station data spread across separate tables with no consolidated view of how the service was actually being used. Before any strategic decision — like where to reposition bikes, which membership tier to invest incentives in, or when to expect signup surges — the underlying data needed to be explored, validated, and joined into a usable shape. The starting point was simply: what does this data actually contain, and can it be trusted?

What I Did

This was structured as an exploratory data analysis (EDA) process — starting from the ground up rather than jumping straight to insights:

  • Scoped the dataset — counted rows across the users, rides, and stations tables to understand overall data volume before analysis.
  • Checked for missing values using COUNTIF across key identifier and timestamp fields, to catch structural gaps before they could silently affect downstream aggregates.
  • Profiled ride summary statistics — min/max/average distance and average ride duration — which is what first surfaced a data quality flag: a minimum ride distance of 0, which shouldn't be possible for a real ride.
  • Quantified likely false starts by explicitly counting rides under 2 minutes and rides with zero recorded distance, rather than assuming the anomaly was a one-off.
  • Segmented ridership by membership tier, joining rides to users to compare total rides, average distance, and average duration between casual and subscribed riders.
  • Identified peak usage hours by extracting the hour from each ride's start time and counting rides per hour across the full dataset.
  • Ranked the most popular stations by joining ride start locations to the stations table and counting rides per station.
  • Analyzed monthly signup trends using DATE_TRUNC on user signup dates, to understand seasonality in new user growth.

Key Insights

1. Data Quality: False Starts

Summary statistics on ride distance surfaced an immediate red flag — a minimum distance of 0km, which isn't a realistic value for a completed ride. Digging further, this was quantified precisely: 106 rides under 2 minutes and 1 ride with exactly zero distance. These were flagged rather than silently included, since leaving them in would understate true average ride duration and distance.

2. Membership Tier Behavior

Casual riders show a notably higher average ride distance and duration than subscribers, which is consistent with tourist or one-off leisure usage rather than routine commuting. This suggests an opportunity: a weekend explorer pass or short-term leisure package could capture more value from this segment. Subscribers, meanwhile, represent the highest total ride volume — the operational backbone of the service — making subscriber retention and incentive programs the higher-leverage lever for sustained revenue, since a small percentage improvement in subscriber churn moves far more rides than the same improvement applied to the casual segment.

3. Peak Demand Hours

Ride volume peaks sharply at two points in the day: 7am and 3pm — matching the start and end of a typical workday rather than a single midday leisure peak. This has a direct operational implication: bike availability at high-demand stations needs to be actively managed around these two windows specifically, not evenly distributed across the day. In practice, that means fleet rebalancing crews should be scheduled to complete restocking runs just ahead of 7am and 3pm, rather than on a flat hourly cadence — the flat approach would waste labor hours during the troughs while still risking stockouts right before each surge.

4. Popular Stations

Ranking stations by ride count highlights which locations see disproportionate demand. Cross-referencing this with the peak-hour finding points toward a clear fleet rebalancing priority: ensure high-traffic stations are stocked ahead of the 7am and 3pm surges specifically, rather than spreading redistribution effort evenly across the whole network. The stations at the top of this list are the ones where a stockout has the highest cost — each missed ride there is a lost trip a competitor (or a rideshare app) is happy to pick up instead, so this ranking is the practical starting point for prioritizing which docks get checked first each morning.

5. Signup Seasonality

Monthly new-signup counts reveal which months drive the most user growth. Understanding this pattern matters operationally — if signups spike in a particular season, bike availability needs to scale ahead of that demand rather than reactively, to avoid new users having a poor first experience with the service. A bad first ride — a bike unavailable at signup, or a long walk to the nearest working dock — is disproportionately costly during a growth month specifically, since it risks souring exactly the cohort the business is trying hardest to convert into long-term subscribers.

Step-by-Step Walkthrough

1. Row counts across core tables

View query 
SELECT 
(SELECT  COUNT (*) FROM data-analyst-project-1-504112.ride_data.users) AS total_users,
(SELECT  COUNT (*) FROM data-analyst-project-1-504112.ride_data.ride_data) AS total_rides, 
(SELECT  COUNT (*) FROM data-analyst-project-1-504112.ride_data.stations) AS total_stations;

2. Checking for missing values

View query 
SELECT 
COUNTIF (event_id IS NULL) AS null_ride_ids,
COUNTIF (user_id IS NULL) AS null_user_ids,
COUNTIF (event_date IS NULL) AS null_event_times
FROM data-analyst-project-1-504112.ride_data.ride_data

3. Summary statistics for rides

View query 
SELECT 
MIN(distance_km) AS min_distance,
MAX(distance_km) AS max_distance,
AVG(distance_km) AS avg_distance,
AVG(TIMESTAMP_DIFF(end_time, start_time, MINUTE)) AS avg_ride_duration_minutes,
COUNT(*) AS total_rides
FROM `data-analyst-project-1-504112.ride_data.rides`;

4. Flagging false-start rides

View query 
SELECT 
COUNTIF(TIMESTAMP_DIFF(end_time, start_time, MINUTE)<2) AS short_rides,
COUNTIF(distance_km=0) AS zero_distance_rides
FROM `data-analyst-project-1-504112.ride_data.rides`;

5. Ridership by membership tier

View query 
SELECT 
u.membership_level,
COUNT(r.ride_id) AS total_rides,
AVG(r.distance_km) AS avg_distance_km,
AVG(TIMESTAMP_DIFF(r.end_time, r.start_time, MINUTE)) AS avg_ride_duration_minutes
FROM `data-analyst-project-1-504112.ride_data.rides` AS r
JOIN `data-analyst-project-1-504112.ride_data.users` AS u 
ON r.user_id = u.user_id
GROUP BY u.membership_level
ORDER BY total_rides DESC;

6. Peak ride hours

View query 
SELECT 
EXTRACT(HOUR FROM start_time) AS start_hour,
COUNT(*) AS ride_count
FROM `data-analyst-project-1-504112.ride_data.rides`
GROUP BY start_hour
ORDER BY start_hour;

7. Most popular stations

View query 
SELECT 
s.station_name,
COUNT(r.ride_id) AS ride_count
FROM `data-analyst-project-1-504112.ride_data.rides` AS r
JOIN `data-analyst-project-1-504112.ride_data.stations` AS s 
ON r.start_station_id = s.station_id
GROUP BY s.station_name
ORDER BY ride_count DESC;

8. Monthly signup trends

View query 
WITH monthly_signups AS ( 
SELECT DATE_TRUNC(created_at, MONTH) AS signup_month,
COUNT(user_id) AS new_signups
FROM `data-analyst-project-1-504112.ride_data.users`
GROUP BY signup_month 
)
SELECT * FROM monthly_signups
ORDER BY signup_month;

Next Steps

Visualizing peak-hour ride volume and monthly signup trends would make both patterns easier to act on operationally — particularly for planning bike redistribution timing and anticipating fleet scaling ahead of high-signup months. A further breakdown of station demand by surrounding area type (business district vs. residential) would also help clarify whether commuter demand and station placement are currently well matched.
