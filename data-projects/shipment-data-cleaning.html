Shipment Data Cleaning, BigQuery SQL

Google BigQuery SQL

Diagnosed and fixed six distinct data quality problems in a raw shipment tracking dataset, using SQL to test where the data could and couldn't be trusted before it reached any downstream report.

Key Results

  • Six distinct data quality issues identified and resolved in a single query: whitespace, inconsistent casing, placeholder null strings, exact duplicates, invalid numeric values, and date logic errors.
  • Exact duplicate rows removed using a windowed ROW_NUMBER() approach, rather than a blunt DISTINCT, so duplication is judged on the full business-meaningful combination of fields rather than row-level noise.
  • Invalid shipment records surfaced, not silently dropped: negative weights are corrected rather than deleted, and shipments where delivery precedes shipping are explicitly flagged as Invalid instead of being hidden from downstream analysis.

The Business Problem

Any report built directly on this shipment tracking data would have been wrong, and worse, wrong in a way that wasn't obvious. Warehouse and carrier names were logged with inconsistent capitalization and stray whitespace, so a group-by on carrier would have split "FedEx" and "fedex " into two separate rows. Exact duplicate shipment records were inflating counts. Weight values were negative or zero. Ship and delivery dates were recorded across multiple formats, some of which weren't valid dates at all. None of these issues would throw an error. They would just quietly produce numbers that looked plausible and were wrong. The core question this project answers: can this data actually be trusted, and if not, what specifically is broken and how much of it is fixable versus flagged?

Plausible Causes

Before touching the data, it's worth naming what typically produces this kind of mess, since the fix depends on the cause:

  • Manual entry inconsistency: free-text fields like warehouse and carrier names are prone to casing and whitespace drift when typed by different people or systems over time.
  • Multiple source systems merged without a shared schema: a literal string "NULL" standing in for a true null, and several different date formats in the same column, both point to data being combined from systems that didn't agree on conventions.
  • No upstream deduplication logic: exact duplicate rows suggest records are being re-inserted, possibly from retries or repeated batch loads, without a uniqueness check.
  • Unvalidated numeric input: negative and zero weight values point to a form or import process that doesn't reject impossible values at the point of entry.

Proof: What the SQL Found and Fixed

A single GoogleSQL query built up in stages, each stage testing one of the causes above:

  • Standardizes text fields: trims whitespace and normalizes casing (INITCAP for city and carrier names, UPPER for state codes) across origin_warehouse, destination_city, destination_state, and carrier. This confirms the manual-entry hypothesis: the raw data did carry exactly this kind of drift.
  • Resolves nulls: converts the literal "NULL" string into a true NULL value for damage_reported, and applies COALESCE to give destination_city and delivery_date readable defaults where missing. Confirms the mixed-source hypothesis.
  • Removes exact duplicates: uses ROW_NUMBER() in a CTE, partitioned on the combination of warehouse, destination, carrier, ship date, weight, and freight cost, keeping the first shipment_id per group. Confirms duplication was present and systematic enough to need a rule, not a one-off manual fix.
  • Fixes invalid numeric values: corrects negative weight_kg entries via ABS() and nulls out zero-weight rows that can't represent a real shipment. Confirms the unvalidated-input hypothesis, and treats negative and zero weight as two different problems rather than one, since a negative value is likely a sign error while a zero value has no safe correction.
  • Validates date logic: parses ship_date and delivery_date with SAFE.PARSE_DATE (so malformed strings return NULL instead of erroring the query), computes transit days via DATE_DIFF, and flags shipments where delivery precedes shipping as Invalid.

Step-by-Step Walkthrough

Built up one issue at a time, each step isolated and verified before folding it into the next:

1. Removing whitespace

View query 
SELECT shipment_id, 
TRIM(origin_warehouse) AS origin_warehouse,
TRIM(destination_city) AS destination_city,
TRIM(destination_state) AS destination_state,
TRIM(carrier) AS carrier
FROM `data-analyst-project-1-504112.dirty_shipments.dirty-shipments`;

2. Standardizing text casing

View query 
SELECT shipment_id, 
INITCAP(TRIM(origin_warehouse)) AS origin_warehouse,
INITCAP(TRIM(destination_city)) AS destination_city,
UPPER(TRIM(destination_state)) AS destination_state,
INITCAP(TRIM(carrier)) AS carrier
FROM `data-analyst-project-1-504112.dirty_shipments.dirty-shipments`;

3. Replacing the string "NULL" and handling true null values

View query 
SELECT shipment_id, 
CASE 
WHEN damage_reported = 'NULL' THEN NULL
ELSE INITCAP(TRIM(damage_reported))
END AS damage_reported,

COALESCE(destination_city, 'Unknown') AS destination_city, 
COALESCE(delivery_date, 'Not Yet Delivered') AS delivery_date,

INITCAP(TRIM(origin_warehouse)) AS origin_warehouse,
INITCAP(TRIM(destination_city)) AS destination_city,
UPPER(TRIM(destination_state)) AS destination_state,
INITCAP(TRIM(carrier)) AS carrier
FROM `data-analyst-project-1-504112.dirty_shipments.dirty-shipments`;

4. Removing exact duplicate rows

View query 
WITH ranked AS (
SELECT *, ROW_NUMBER() OVER ( 
PARTITION BY origin_warehouse, destination_city, carrier, ship_date, CAST(weight_kg AS STRING), CAST(freight_cost AS STRING)
ORDER BY shipment_id
) AS row_number
FROM `data-analyst-project-1-504112.dirty_shipments.dirty-shipments`
)
SELECT * EXCEPT (row_number)
FROM ranked
WHERE row_number = 1;

5. Fixing negative and suspicious numeric values

View query 
SELECT shipment_id,
CASE 
WHEN weight_kg < 0 THEN ABS(weight_kg)
WHEN weight_kg = 0 THEN NULL 
ELSE weight_kg
END AS weight_kg_cleaned
FROM `data-analyst-project-1-504112.dirty_shipments.dirty-shipments`;

6. Validating date logic (delivery after ship date)

View query 
SELECT shipment_id, ship_date, delivery_date,
DATE_DIFF(
SAFE.PARSE_DATE("%Y-%m-%d", delivery_date),
SAFE.PARSE_DATE("%Y-%m-%d", ship_date),
DAY
) AS transit_days,
CASE 
WHEN SAFE.PARSE_DATE("%Y-%m-%d", delivery_date) < SAFE.PARSE_DATE("%Y-%m-%d", ship_date) THEN 'Invalid'
WHEN SAFE.PARSE_DATE("%Y-%m-%d", delivery_date) = SAFE.PARSE_DATE("%Y-%m-%d", ship_date) THEN 'Same Day Delivery'
ELSE 'Valid'
END AS data_quality_flag
FROM `data-analyst-project-1-504112.dirty_shipments.dirty-shipments`;

Known Limitation and Recommendations

delivery_date contains multiple date formats in the source data (YYYY-MM-DD, MM/DD/YYYY, YYYY/MM/DD, Month DD YYYY, plus a non-date placeholder for undelivered shipments). SAFE.PARSE_DATE is currently set to one format pattern, so rows in other formats parse to NULL and their transit_days and data_quality_flag can't be reliably computed. Those rows currently fall through to a default Valid flag rather than being caught explicitly. This is a real gap worth stating plainly rather than glossing over: the pipeline currently understates how many rows are actually unparseable. Recommended next step is to add format detection (or a COALESCE across multiple SAFE.PARSE_DATE patterns) and an explicit Unparseable flag branch, so that rows which can't be validated are visibly separated from rows confirmed valid, rather than defaulting into the same bucket.

WITH ranked AS (
  SELECT *, 
    ROW_NUMBER() OVER ( 
      PARTITION BY origin_warehouse, destination_city, carrier, ship_date, 
                   CAST(weight_kg AS STRING), CAST(freight_cost AS STRING)
      ORDER BY shipment_id
    ) AS row_number
  FROM `data-analyst-project-1-504112.dirty_shipments.dirty-shipments`
)
SELECT 
  shipment_id,
  CASE 
    WHEN damage_reported = 'NULL' THEN NULL
    ELSE INITCAP(TRIM(damage_reported))
  END AS damage_reported,
  COALESCE(INITCAP(TRIM(destination_city)), 'Unknown') AS destination_city,
  COALESCE(delivery_date, 'Not Yet Delivered') AS delivery_date,
  INITCAP(TRIM(origin_warehouse)) AS origin_warehouse,
  UPPER(TRIM(destination_state)) AS destination_state,
  INITCAP(TRIM(carrier)) AS carrier,
  ship_date,
  CASE 
    WHEN weight_kg < 0 THEN ABS(weight_kg)
    WHEN weight_kg = 0 THEN NULL 
    ELSE weight_kg
  END AS weight_kg_cleaned,
  DATE_DIFF(
    SAFE.PARSE_DATE("%Y-%m-%d", delivery_date),
    SAFE.PARSE_DATE("%Y-%m-%d", ship_date),
    DAY
  ) AS transit_days,
  CASE 
    WHEN SAFE.PARSE_DATE("%Y-%m-%d", delivery_date) < SAFE.PARSE_DATE("%Y-%m-%d", ship_date) THEN 'Invalid'
    WHEN SAFE.PARSE_DATE("%Y-%m-%d", delivery_date) = SAFE.PARSE_DATE("%Y-%m-%d", ship_date) THEN 'Same Day Delivery'
    ELSE 'Valid'
  END AS data_quality_flag
FROM ranked
WHERE row_number = 1;
